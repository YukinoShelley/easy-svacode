> 角色:分析器开发(SVA-server · C++17 / FFmpeg / ONNX Runtime);对应 `docs/团队分工介绍.md` 角色 3(双线集成)。

## 一、任务目标

两条增量开发线,全部**只增不改**:
- **任务 A 睡岗检测集成**:YOLO-Pose 关键点模型接入 C++ 推理管线,持续低头时序判定,产出 `behaviorType="sleep_post"` 告警,复用现有截图/录像/上报链路。
- **任务 B 国标视频流兼容**:GB28181 设备流经 ZLMediaKit 分发后进入现有解码推理管线——本次**零代码改动**,仅契约 + 验证。

## 三、硬性红线(强制约束,违反即返工)

- **R1 纯增量**:只新增代码块/新字段(带默认值)/新文件/新成员;新增逻辑仅在 `keypointsPresent=true` 或 `sleep_post` 规则被配置时激活。
- **R2 现有代码行零修改**:现有行一字不改;允许的形态仅为"函数末尾/分支链之间**插入**新代码块"。
- **R3 不破坏原有功能**:老解码器/老规则/追踪器/告警/拉流路径行为不变;pose 模型缺失时分析器照常启动(仅告警)。
- **R4 不大量修改**:任务 B 零代码;需重构现有代码的优化一律进 Backlog,不得顺手实现。
- **R5 权威参照**:每处借鉴须对照本手册第五节"代码级参考映射"的项目与 文件:行号。
- **R6 仓库既有规则照旧**:live-output 双 key、CPU 构建 `-DSVA_ONNXRUNTIME_GPU=OFF`、nvenc→x264 回退等 AGENTS.md 规则不得回退;构建产物不入库。

### A.9 睡岗判定数据流(链路核对图)

```
解码帧 → Pose 解码(框+17关键点+俯角)→ DetectObject
  → 时态追踪(每 track:关键点 EMA → 俯角历史)
  → BehaviorEvaluator(sleep_post:窗口内最长连续低头段 ≥ thresholdMs)
  → happen=true/behaviorType=sleep_post → DetectFrameEvent → 后端建告警
  → bind-media → GenerateAlarmVideo(截图/录像)→ 回调后端 → 入库
```

## 六、任务 B:国标视频流兼容(本次零代码,仅契约+验证)

- **B1 契约**:官方 ZLM 只做国标媒体收流(app 固定 `rtp`;openRtpServer 以 port+stream_id 绑端口为流 ID),**不内置 SIP**;SIP 由流媒体角色实现(参考第五节)。→ 国标流在 ZLM 内命名 `rtp/{国标流ID}`;后端 buildStreamUrl 国标分支按此拼;分析器只认 streamUrl、不调 ZLM REST。
- **B4 验证**:H.265(官方确认收流支持 h264/h265/aac/g711/opus;确认 deps ffmpeg-6.1.4 hevc)、http-flv 地址、断线重连恢复、RTSP 老设备回归——纯测试。
