# 团队开发分工介绍

> 本文档介绍小组在 easySVA 二次开发中的**开发设计分工**。
> 分工围绕两大增量开发任务（GB28181 国标接入、睡岗检测算法）展开，全部成员均承担程序开发设计工作；
> 环境部署、PPT、文档、演示视频等公共事务由全员协作完成，不占用开发分工。

---

## 一、分工总原则

1. **开发设计为核心**：每个成员都有明确的代码开发任务（流媒体 C++ / 算法 / 分析器 C++ / 后端 Java / 前端 Vue），课程看重的软件系统开发能力是分工主线
2. **双线并行**：GB28181 国标接入线与睡岗检测线互不依赖、并行开发，由后端、前端两位同学双线支撑
3. **增量开发**：基于原项目做加法，新功能以"新增模块/表/接口"为主，不破坏原有逻辑
4. **接口契约先行**：开发前先约定字段、接口、算法编码等契约，避免返工

## 二、五人开发角色总览

| 角色 | 技术方向 | 开发主责 | 对应任务线 |
|---|---|---|---|
| 1. 流媒体开发 | C++ / ZLMediaKit / SIP | SVA-mediaServer GB28181 接入能力开发 | 国标接入线 |
| 2. AI 算法开发 | Python / YOLO-Pose / ONNX | 睡岗检测算法设计、模型导出与调优 | 睡岗检测线 |
| 3. 分析器开发 | C++ / FFmpeg / ONNX Runtime | SVA-server 算法集成与告警链路开发 | 双线（算法集成 + 国标流兼容） |
| 4. 后端开发 | Java / Spring Boot / MyBatis | 设备/布控/告警业务接口与数据库开发 | 双线 |
| 5. 前端开发 | Vue 2 / Element UI / flv.js | 设备管理、布控配置、告警展示页面开发 | 双线 |

> 组长由流媒体开发或后端开发兼任，负责架构决策与代码评审。

## 三、角色职责详述（开发设计部分）

### 角色 1：流媒体开发（C++ / ZLMediaKit / SIP）— 国标接入线主责

**目标**：让 SVA-mediaServer 支持 GB/T 28181 国标设备 SIP 注册与 RTP 收流。

**开发任务**：
- 移植 ZLMediaKit 官方 GB28181 模块（SIP 服务：设备注册/保活/注销信令，5060 端口）至 SVA-mediaServer，补齐缺失的 `src/GB28181` 模块与 `[gb28181]` 配置段
- 打通 RTP PS 流接收链路：复用现有 `GB28181Process` 解包，将国标设备 RTP 推流转为内部标准流，注册进 ZLM 流媒体分发
- 验证/适配 ZLM GB28181 REST 接口（getMediaList 获取在线国标设备与通道、播放地址生成）
- 回归验证既有魔改功能：时移告警录像（startRecordTask back_ms/forward_ms）、电视墙拼接（stack/*）不受影响
- 提供国标设备播放 URL 生成方案（rtsp/ws-flv），供分析器与前端使用

**设计要点**：SIP 信令线程与媒体线程隔离；设备编码（20 位国标 ID）作为流名规范；H.265 流兼容方案（转码或直通）。

**代码交付**：SVA-mediaServer 新增 GB28181 模块代码、config.ini 配置、接口联调说明。

---

### 角色 2：AI 算法开发（Python / YOLO-Pose / ONNX）— 睡岗检测线主责

**目标**：完成睡岗检测算法设计、原型验证、模型导出与参数调优。

**开发任务**：
- 基于预训练 YOLO-Pose（如 yolov8n-pose / yolov11n-pose，COCO 17 关键点）搭建 Python 推理原型
- 设计**头部姿态判定算法**：由关键点（耳、肩、鼻、颈）几何计算头部俯仰/低头角度
- 设计**多帧时序判定逻辑**：持续低头超过阈值时长（如 N 秒）判定为睡岗，过滤瞬时低头、弯腰取物等干扰；输出判定结果与置信度
- 模型导出 ONNX，输出格式对齐分析器解码器（DenseWithNms 格式），验证精度与速度
- 阈值参数化（角度阈值、持续时长、置信度），预留调优入口；本地视频/摆拍样本测试，降低误报

**设计要点**：判定逻辑"规则为主、模型为辅"（预训练模型只出关键点，睡岗判断由规则完成，无需训练数据）；时序状态机设计（正常→低头→持续→睡岗→恢复）。

**代码交付**：Python 原型脚本、ONNX 模型、角度/时序算法说明文档。

---

### 角色 3：分析器开发（C++ / FFmpeg / ONNX Runtime）— 双线集成

**目标**：将睡岗算法集成进 SVA-server 推理管线，并兼容国标视频流。

**开发任务**：
- 扩展 `AlgorithmOnYolo` 推理框架：支持加载 YOLO-Pose 关键点模型，新增算法编码（如 `on_yolo11n_pose_sleep`），复用模型加载、预处理、后处理框架
- 扩展检测结果结构（DetectObject）支持关键点数据；实现 C++ 侧角度计算与睡岗时序判定（复用 `TemporalContext` 时态追踪做持续状态计时）
- 打通睡岗告警链路：命中睡岗规则 → 复用 `GenerateAlarmVideo` 告警截图/视频 → 经 `Scheduler` 上报后端
- 兼容国标流：布控任务下发时支持国标设备的播放地址（由流媒体开发提供），统一进入解码推理管线
- 与后端约定布控请求参数：algorithmTasks 增加睡岗算法与目标（target_codes）

**设计要点**：不改动原有算法框架主流程，新算法以"新增子类/注册"方式接入；关键点后处理与普通检测分支共存。

**代码交付**：SVA-server 新增算法模块代码、ONNX 集成构建脚本、告警上报联调。

---

### 角色 4：后端开发（Java / Spring Boot / MyBatis）— 双线

**目标**：提供国标设备管理与睡岗告警的全部后端能力。

**开发任务**：
- **数据库设计**：device/h_device 表扩展字段 `device_type`（rtsp/gb28181）、`gb_device_id`、`gb_platform_id`；新增国标设备相关表或复用现有表
- **国标设备同步接口**：调用 ZLM GB28181 REST 接口拉取在线设备/通道列表，支持"一键导入"进平台设备表；定时任务刷新设备在线/离线状态并落库
- **布控任务扩展**：布控接口支持国标设备与睡岗算法（deployment_task_algorithm 增加睡岗检测目标选项），国标/RTSP 设备统一对待
- **睡岗告警业务**：新增"睡岗告警"类型（h_waring_type/字典数据）；告警上报接口（addFromSvaSimple）兼容睡岗事件字段；告警查询/统计接口
- 与原 AI 复核链路对接：睡岗告警同样进入大模型复核流程

**设计要点**：字段扩展向后兼容（默认值兜底）；同步接口幂等（按国标编码去重）；设备状态同步用定时轮询 + 状态机。

**代码交付**：数据库变更 SQL、Mapper/Service/Controller 新增代码、接口文档（Swagger）。

---

### 角色 5：前端开发（Vue 2 / Element UI / flv.js）— 双线

**目标**：完成国标设备管理与睡岗检测的页面功能。

**开发任务**：
- **设备管理页**：设备列表区分 RTSP/GB28181 类型展示（类型标签、来源标识）；新增"从流媒体同步国标设备"按钮（调用后端同步接口，弹窗勾选导入）
- **国标设备预览**：设备详情/视频预览页支持国标设备播放（ws-flv 播放地址，H.265 流处理方案）
- **布控配置页**：布控任务新增"睡岗检测"选项（算法/目标选择联动后端配置），规则参数表单（角度阈值、持续时长等，若后端透传）
- **告警展示**：告警列表/详情支持睡岗告警类型展示（类型名、截图、视频）；告警统计/大屏图表适配新类型
- 设备在线状态展示与刷新

**设计要点**：页面组件化复用（告警表格、设备表单）；新增 API 封装统一走 axios 请求层；类型/字典数据驱动展示，避免硬编码。

**代码交付**：Vue 页面与组件代码、API 封装、路由/菜单注册。

## 四、角色间协作与接口契约（开发设计约定）

```
                    ┌─────────────┐
                    │ 2.AI算法开发 │── ONNX模型/判定规则 ──→ 3.分析器开发
                    └─────────────┘        (契约: 输出格式/算法code)
                          │
  1.流媒体开发 ──播放URL/设备列表──→ 4.后端开发 ←── 接口字段 ──→ 5.前端开发
  (契约: 流名规则/同步接口)      (契约: REST接口/JSON字段/表结构)
                          │
                  3.分析器开发 ──告警上报字段──→ 4.后端开发
                  (契约: 布控请求参数/告警事件字段)
```

**关键契约清单**（开发前必须先定）：

| 契约 | 参与角色 | 内容 |
|---|---|---|
| 算法编码 | 2/3/4 | 睡岗算法 code（如 `on_yolo11n_pose_sleep`）、目标类别名 |
| ONNX 输出格式 | 2/3 | 张量形状、解码方式（对齐 DenseWithNms） |
| 布控请求参数 | 3/4 | algorithmTasks 结构、睡岗检测目标字段 |
| 告警上报字段 | 3/4 | 睡岗事件的事件键/行为类型/规则 ID 命名 |
| 同步接口 | 1/4 | ZLM→后端：getMediaList 拉取与导入接口路径、字段映射 |
| 页面接口 | 4/5 | 设备列表/导入/预览地址/告警查询接口与 JSON 结构 |

## 六、公共事务说明（不占开发分工）

以下事务**不属于开发分工**，由全员利用开发间隙协作完成，组长统筹：
- 环境部署（WSL2/Ubuntu 22.04 一键安装脚本）、Fork 仓库与 Star
- 设计文档、部署手册、演示视频、展示 PPT
- 考勤打卡、组内互评材料

> 分工的核心逻辑：**每个成员都有一块完整的"设计→编码→联调"开发闭环**，公共事务只是辅助，课程评分的重点（软件系统 40% + 交付物 20%）全部落在开发成果上。
